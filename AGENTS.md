# AGENTS.md — «Как же так, Олег!»

Инструкции для ИИ-агентов, работающих с этим репозиторием. Приоритет: сохранить играбельность, канонический визуальный стиль, историю Git и минимальный масштаб изменений. Если текущий код расходится с описанием ниже, проверь актуальный `main` и сообщи о расхождении, не подгоняй код молча.

## Продукт

Юмористическая браузерная LCD-игра в духе советских электронных игр 1980-х: Олег ловит стартапы, которые бросают инвесторы. Сохранять ретрохарактер, абсурдный юмор и существующие игровые механики. Не пересоздавать проект.

## Исходники и запуск

- Сайт — статические `index.html`, `styles.css`, `game.js` **в корне репозитория**.
- Спрайты: `assets/` — каноническая папка PNG.
- Реплики: `resources/oleg-exclamations.json`; группы `catch`, `unicorn`, `toxic`.
- Тесты: `tests/`.
- Публикация PR: `.github/workflows/pr-preview.yml`. При публикации workflow копирует необходимые корневые файлы и каталоги во временную `.publish/`.
- Не создавай и не поддерживай вторую копию графики в `dist/assets/`: `dist/` более не является источником актуальной версии.
- Для локального запуска используй статический HTTP-сервер из корня, например `python3 -m http.server 8000`; `file://` не подходит, поскольку JSON загружается через `fetch`.

## Git: безопасность и публикация

- `main` — стабильная ветка. Не коммитить туда изменения напрямую; не делать merge без явного разрешения пользователя.
- Для каждой задачи — отдельная **локальная** ветка от актуального `main`, небольшие осмысленные коммиты. Если у рабочей копии уже есть незакоммиченные изменения — не терять их и прежде спросить.
- Разработка, поиск, правки и тесты — локально, **если реально доступна рабочая копия**. Не заявляй о доступе к Mac из облачной среды без проверки.
- Push рабочей ветки и PR — когда пользователь попросил тестовую ссылку или публикацию ветки. GitHub Actions создаёт preview из PR.
- Проверка PR Preview обязательна до одобрения релиза; зелёный CI не заменяет визуальное тестирование.
- `gh-pages` — публикационная ветка, обычные игровые правки в неё не вносить.
- Запрещены `git reset --hard`, принудительный push, удаление чужих изменений и изменение защиты веток без отдельного разрешения.

## Визуальные правила

Референсы проекта (если предоставлены в рабочей среде): **«Олег — визуальный паспорт персонажа.png»** и **«Палитра игры.png»**. Если они недоступны и задача требует генерации/замены внешности, запросить их, а не фантазировать.

**Олег:** свободные вьющиеся пряди (не шарообразная афропричёска), тонкие круглые очки, полная тёмная борода и усы, свободная чёрная футболка, прямые укороченные тёмные брюки, массивные белые кроссовки; пропорции по паспорту. Не менять без прямого запроса.

**Палитра новых ассетов:** `#111411` (контур/текст), `#1A1F1A` (тёмная одежда), `#C9CCBA` (кожа/коробки), `#E8E6D8` (светлые элементы), `#F4F2E7` (фон интерфейса). Для **новой** графики не вводить дополнительные цвета, градиенты, текстуры и полупрозрачные заливки без явного указания. Не выполнять автоматическую перекраску уже утверждённых игровых PNG.

Новые игровые спрайты — PNG с прозрачным фоном, без подписей и подложек; без обрезанных частей и пересечений кадров. Сохранять опорные точки, масштаб и читаемость.

## Анимации (текущее состояние v3; проверять код перед изменением)

- Три типа инвесторов, **7 кадров** на горизонтальный спрайтшит, исходный PNG **2048×292**: `investor-young-7-frames-v3.png`, `investor-businesswoman-7-frames-v3.png`, `investor-banker-7-frames-v3.png`.
- Три типа предметов, **6 кадров**, PNG **2048×341**: `item-box-normal-6-frames-v3.png`, `item-box-toxic-6-frames-v3.png`, `item-unicorn-6-frames-v3.png`.
- Границы равных ячеек: `round(i * width / frameCount)`; без индивидуального alpha-crop. Не менять масштаб между кадрами.
- Инвесторы: появление из-за парапета на первом кадре → кадры 2–6 (бросок на шестом) → уход вниз за парапет на последнем кадре. Базовый масштаб 80%, вход/выход около 200 мс. Точный рендеринг/зеркалирование определяется **актуальным кодом**: справа в последней v3-реализации предусмотрено отражение, не отменять его без отдельной задачи.
- Обычная коробка и единорог: циклические 6 кадров + вращение при движении; масштаб 65%.
- Токсичная коробка: однократные кадры 1–6 → удерживать последний кадр; дальнейшее вращение при необходимости медленное; масштаб 65%.
- Четыре траектории Безье для четырёх направлений. Рендеринг и детекция поимки должны пользоваться согласованной геометрией. Не вводить ожидание/зависание в конце траектории.
- Зелёные квадраты и линии на композиционных референсах — **только направляющие**. Никогда не переносить их в игровые ассеты или UI.

## Проверка перед локальным коммитом

Для изменений JS / спрайтов по применимости:

```bash
node --check game.js
node tests/smoke_game_runtime.js
python3 tests/verify_sprite_animation_v3.py
git diff --check
```

Дополнительно для графических правок: размеры/alpha PNG, корректность нарезки, отсутствие графических скачков, тест игры через локальный HTTP-сервер. Для правок JSON — проверить валидность JSON и запуск игры. Если тесты изменились, сначала изучи актуальные команды.

## Бережливая работа с контекстом

1. Уточни изменяемое поведение, прежде чем трогать файлы.
2. Найди конкретные символы/функции поиском (`rg`), открывай ограниченные фрагменты, а не огромный `game.js` целиком.
3. Меняй только затронутые файлы; без переименований, чистки или рефакторинга «заодно».
4. Визуальные ассеты передавай/читай повторно только при необходимости.
5. Отчёт короткий: **изменённые файлы; результат тестов; локальный статус или PR/preview; риски**. Большие логи — только по запросу или при ошибках.
6. Для изменения параметров сначала найди существующие константы. Не создавай систему конфигов и сборки только ради одной настройки.

## Чего не делать без отдельного запроса

- Не менять внешность Олега и утверждённые PNG, игровую механику, баланс, управление, фон, звуки, достижения или экран проигрыша, если задача о другом.
- Не менять инфраструктуру GitHub Pages или структуру каталогов без отдельного плана.
- Не удалять старые файлы, если их использование не проверено.
- Не выполнять push/merge/deploy «по привычке»: отделять локальную разработку от удалённой публикации.
