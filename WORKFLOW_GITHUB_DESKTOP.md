# Как же так, Олег! — локальная разработка и публикация через GitHub Desktop

**Статус:** постоянные правила работы для ChatGPT Work / ИИ-агента. Обновлено: без автоматического создания веток.  
**Репозиторий:** `mertvetsov/kak-zhe-tak-oleg`  
**Принцип:** локальные файлы — место разработки; GitHub — удалённая копия и публикация проверенных изменений.

## 1. Обязательный способ работы

1. Используй **локальную рабочую копию** `kak-zhe-tak-oleg` на Mac для чтения, редактирования и проверки игры.
2. Для действий с Git и удалённым GitHub используй **только графическое приложение GitHub Desktop**: выбор репозитория, создание/переключение веток, просмотр diff, commit, fetch, pull, push.
3. **Не используй** для Git/GitHub-операций браузер, встроенный браузер, GitHub connector/plugin, GitHub API, терминал, `git` CLI или `gh` CLI. Не заменяй GitHub Desktop другим инструментом без отдельного явного разрешения пользователя.
4. Если Work не может видеть или управлять локальными файлами либо GitHub Desktop, **остановись и попроси разрешение/действие пользователя**. Не утверждай, что выполнил операцию, если не выполнил её.
5. **Не изменяй `main` напрямую без явного разрешения.** Не отправляй изменения в облако, пока пользователь явно не попросит публикацию/тестовую ссылку. Не выполняй merge без отдельного одобрения.
6. **Не создавай новую ветку автоматически.** По умолчанию продолжай работу в существующей локальной рабочей ветке, даже если пользователь дал новую небольшую задачу. Новая ветка допустима только по прямому запросу пользователя.
7. Если сейчас выбрана `main`, не редактируй файлы и не коммить в неё: через Desktop проверь наличие другой рабочей ветки, предложи перейти на неё и запроси подтверждение. Если рабочей ветки нет — попроси разрешение на создание одной; не создавай её молча.
8. Используй `AGENTS.md` и другие правила проекта; при расхождении этих правил с более поздней прямой командой пользователя уточни намерение.

## 2. Старт каждой задачи (локально)

1. Открой локальную папку проекта и установи, к какому репозиторию она относится. Не клонируй второй экземпляр без необходимости.
2. Через **GitHub Desktop** выбери `kak-zhe-tak-oleg`, проверь **Current branch** и вкладку **Changes**. Если есть чужие/незавершённые изменения, не сбрасывай и не перезаписывай их: сообщи пользователю.
3. Если нужно обновить стабильную базу, используй **Fetch origin**, затем **Pull origin** в Desktop. Не делай pull при конфликте или риске потери локальных изменений без согласования.
4. **Не создавай ветку для очередной задачи.** Если активна существующая рабочая ветка — продолжай в ней, сохраняя несколько мелких улучшений локальными коммитами. Если открыта `main`, сначала предложи переключиться на уже существующую рабочую ветку. Если такой нет — спроси разрешение на создание (например, `work/ongoing`). Создавай отдельную новую ветку (`feature/...`, `fix/...`) только по прямой команде пользователя.
5. Перед продолжением работы проверь, нет ли уже открытого PR и не относится ли текущая ветка к завершённому PR. Если PR уже слит или закрыт, не переиспользуй старую ветку для новых несвязанных изменений без согласования.
6. Читай только файлы, связанные с задачей; не исследуй заново весь проект при каждой небольшой правке.

## 3. Локальная разработка

1. Меняй файлы непосредственно в рабочей папке Mac.
2. Не пересоздавай проект, не выполняй большой рефакторинг без запроса и не заменяй рабочие ассеты без необходимости.
3. Исходники и спрайты располагаются в корне проекта (`index.html`, `styles.css`, `game.js`, `assets/`, `resources/`). Старую папку `dist/` не восстанавливай: предпросмотр формируется workflow публикации.
4. Для новой графики соблюдай визуальный паспорт Олега, палитру и соглашения по нарезке кадров.
5. Двигайся небольшими шагами; после каждой существенной правки проверяй локальный результат.

## 4. Локальные проверки — до GitHub

**Никакой push ради проверки.** Проверяй игру на Mac.

### 4.1 Запуск игры

Открой приложение/среду, которая может обслуживать локальную папку по HTTP (локальный статический сервер), и перейди на локальный адрес, который оно реально выдаст. **Не открывай `index.html` через `file://`**: игровые ресурсы загружаются через `fetch`.

Если запуск сервера или тестового раннера доступен только через терминал, **не запускай его без отдельного разрешения**. Сообщи, какие проверки из-за этого недоступны, и предложи пользователю один раз настроить GUI-способ локального запуска. Не выдумывай, что тесты прошли.

### 4.2 Что проверять

- Игра загружается; кнопка старта работает; ассеты и JSON доступны.
- Изменённая механика работает; остальные ключевые сценарии не сломаны.
- Графика отображается без обрезания, с правильной прозрачностью/масштабом.
- Управление и интерфейс работают на применимых размерах экрана.
- В проекте уже существуют тесты `tests/verify_sprite_animation_v3.py` и `tests/smoke_game_runtime.js`. Запускай их через разрешённую локальную среду/GUI-runner при её наличии; не выдавай «прошли», если не запускал.

### 4.3 Если локального тестирования нет

Остановись на проверенной стадии, перечисли, что смог проверить визуально/статически, и что осталось непроверенным. Не создавай PR как замену обязательным локальным тестам без согласования.

## 5. Локальный commit через GitHub Desktop

1. Во вкладке **Changes** проверь список файлов и diff; убедись, что нет случайных картинок, секретов, временных файлов или изменений не по задаче.
2. Впиши короткий осмысленный **Summary** и при необходимости Description.
3. Нажми **Commit to <рабочая ветка>**. Коммит остаётся **локальным**, пока не выполнен push. Если текущая ветка — `main`, остановись и согласуй переход в рабочую ветку.
4. При следующих правках повторяй цикл редактирование → тестирование → commit в **той же ветке**, в том числе для новых мелких задач. Не создавай новую ветку и отдельный PR на каждую мелочь.
5. Сообщай пользователю, что готова локальная версия, с коротким списком изменений и реально выполненных тестов.

## 6. Когда пользователь просит тестовую ссылку

1. Убедись, что локальные проверки закончены и рабочая ветка (не `main`) выбрана в GitHub Desktop. Перед push покажи пользователю состав накопленных изменений: одна рабочая ветка может содержать несколько мелких задач. Если часть изменений пока публиковать нельзя — остановись и согласуй разделение.
2. В Desktop нажми **Publish branch** (для новой ветки) или **Push origin** (если ветка уже опубликована).
3. Это первый момент, когда изменения отправляются на GitHub. `main` не затрагивается.
4. Для PR требуется отдельное действие: GitHub Desktop предоставляет **Create Pull Request / Preview Pull Request**, но в ряде версий завершение создания PR **открывает браузер**. **Не обходи запрет автоматически**. Если Desktop не позволяет завершить PR внутри приложения, остановись и попроси пользователя либо самому завершить PR, либо разово разрешить открытие веб-страницы. Без разрешения не используй браузер/API/CLI.
5. После фактического создания PR существующий GitHub Actions `Publish PR preview` публикует тестовую версию. Нельзя утверждать, что она доступна, пока публикация не подтверждена.
6. Сообщи номер PR и ссылку на предпросмотр только после подтверждения (или пометь ссылку как ожидаемую, не как проверенную).
7. Правки по обратной связи выполняй локально в той же ветке → проверяй → commit → **Push origin** через Desktop после согласования. Не создавай новый PR без необходимости.
8. После merge согласуй, какую существующую рабочую ветку использовать для следующего цикла. Не продолжай бесконтрольно коммитить в ветку завершённого PR.

## 7. Публикация в стабильную версию

1. Пользователь проверяет тестовую игру и **явно разрешает merge**.
2. GitHub Desktop не предоставляет во всех версиях самостоятельное полное слияние удалённого PR с веткой `main`. **Не имитируй эту операцию и не заменяй её скрытым веб/CLI-вызовом.** Если нет нативного способа, попроси пользователя выполнить merge вручную на странице PR либо запроси одноразовое исключение.
3. После подтверждённого merge: в Desktop выбери `main` → **Fetch origin** → **Pull origin**; убедись, что локальная `main` обновлена.
4. Ветка `gh-pages` обслуживает публикацию и предпросмотры; не редактируй её напрямую.
5. По возможности проверь опубликованную игру в обычном браузере **как пользовательское тестирование**, но не выполняй через него никаких Git/GitHub-операций. Если запрет распространяется вообще на браузер, попроси пользователя проверить ссылку самостоятельно.

## 8. Стоп-условия и безопасность

Немедленно остановись и сообщи пользователю, если:

- GitHub Desktop недоступен для управления;
- локальный репозиторий не найден;
- в рабочей папке имеются незнакомые незакоммиченные изменения;
- выбрана `main`, а рабочая ветка не согласована;
- текущая ветка связана с уже завершённым PR и нужна новая итерация;
- требуется операция, не поддерживаемая GUI Desktop (например, завершение PR или merge), а исключение не дано;
- возник конфликт, отказ авторизации или проблема с push;
- тесты нельзя выполнить разрешёнными инструментами.

Никогда не сбрасывай, не удаляй и не перезаписывай незнакомые изменения автоматически. Не делай force push. Не пушь в `main` напрямую.

## 9. Экономия токенов и короткая отчётность

- Для точечной задачи изучай только релевантные файлы и локальный diff.
- Не повторяй полный аудит архитектуры на каждую мелочь.
- Не запускай браузерную навигацию и GitHub API для выяснения того, что видно локально.
- Не публикуй каждую правку: сначала проведи несколько локальных итераций.
- Не создавай ветку при каждом новом запросе: по умолчанию используй текущую активную рабочую ветку.
- В отчёте достаточно: **что изменено; что проверено; локальная ветка/коммит; что нужно от пользователя дальше**.
- Не трать время на массовое переписывание инструкций и тестов без необходимости.

1. Передай этот файл в Work вместе с текущим `AGENTS.md`.
2. Попроси Work добавить раздел 10 в корневой `AGENTS.md`, не удаляя другие инструкции и не дублируя существующее.
3. Пусть Work подтвердит наличие локальной папки и доступ к **GitHub Desktop**. Пока ничего не публиковать.
4. Выберите одну существующую рабочую ветку для серии небольших задач; новую не создавайте без отдельного запроса. Первую задачу проведите полностью локально; к push переходите отдельно.
